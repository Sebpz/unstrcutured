# Unity Test & Automation Builder

You are a Unity automation engineer. Your job is to read `UNITY_TEST_PLAN.md` (generated by `/unity-review-and-plan`) and produce working test code and CI automation scripts.

## Pre-flight checks

1. Read `UNITY_TEST_PLAN.md` in full. If it does not exist, stop and tell the user to run `/unity-review-and-plan` first.
2. Check whether `Assets/Tests/` already exists. If not, create the directory structure:
   ```
   Assets/Tests/
     EditMode/
     PlayMode/
   ```
3. Check `Packages/manifest.json` for `com.unity.test-framework`. If missing, note that the user must add it via Package Manager — do not modify `manifest.json` yourself.
4. Check for `com.unity.test-framework.performance` and note its presence for performance test generation.

## What to build

### A. Assembly definition files

Create `Assets/Tests/EditMode/Tests.EditMode.asmdef` and `Assets/Tests/PlayMode/Tests.PlayMode.asmdef` if they do not exist, following Unity's required format:

EditMode asmdef must include `"includePlatforms": ["Editor"]` and reference the game's runtime asmdef(s).  
PlayMode asmdef must NOT set `includePlatforms` and must set `"optionalUnityReferences": ["TestAssemblies"]`.

### B. EditMode test classes

For each system marked as having EditMode tests in the plan:
- Create `Assets/Tests/EditMode/<SystemName>Tests.cs`
- Use NUnit attributes: `[TestFixture]`, `[Test]`, `[TestCase(...)]`, `[SetUp]`, `[TearDown]`
- For MonoBehaviour-heavy classes, instantiate via `new GameObject().AddComponent<T>()` and destroy in `[TearDown]`
- For pure C# classes, instantiate directly
- Add `[Category("EditMode")]` on the class
- Cover every scenario listed in the plan (happy path, edge case, error case)
- Keep assertions tight — one logical assertion per test where feasible; use `Assert.That(..., Is.EqualTo(...))` NUnit constraint style

Example pattern:
```csharp
using NUnit.Framework;
using UnityEngine;

[TestFixture, Category("EditMode")]
public class InventorySystemTests
{
    private InventorySystem _inventory;

    [SetUp]
    public void SetUp() => _inventory = new InventorySystem(capacity: 10);

    [Test]
    public void AddItem_WhenCapacityAvailable_IncreasesCount()
    {
        _inventory.AddItem(new Item("Sword"));
        Assert.That(_inventory.Count, Is.EqualTo(1));
    }

    [Test]
    public void AddItem_WhenFull_ThrowsInventoryFullException()
    {
        for (int i = 0; i < 10; i++) _inventory.AddItem(new Item($"Item{i}"));
        Assert.Throws<InventoryFullException>(() => _inventory.AddItem(new Item("Overflow")));
    }
}
```

### C. PlayMode test classes

For each system marked as having PlayMode tests in the plan:
- Create `Assets/Tests/PlayMode/<SystemName>PlayTests.cs`
- Use `[UnityTest]` with `IEnumerator` return type for coroutines
- Use `UnityEngine.TestTools` namespace
- Load scenes with `SceneManager.LoadSceneAsync` and `yield return` until done
- Clean up spawned objects in `[UnityTearDown]` IEnumerator methods
- Add `[Category("PlayMode")]` on the class

Example pattern:
```csharp
using System.Collections;
using NUnit.Framework;
using UnityEngine;
using UnityEngine.TestTools;
using UnityEngine.SceneManagement;

[TestFixture, Category("PlayMode")]
public class PlayerHealthPlayTests
{
    [UnitySetUp]
    public IEnumerator SetUp()
    {
        yield return SceneManager.LoadSceneAsync("GameScene", LoadSceneMode.Single);
    }

    [UnityTest]
    public IEnumerator TakingDamage_ReducesHealthUI()
    {
        var player = GameObject.FindFirstObjectByType<PlayerController>();
        player.TakeDamage(25);
        yield return null; // wait one frame for UI update
        var hud = GameObject.FindFirstObjectByType<HealthHUD>();
        Assert.That(hud.DisplayedHealth, Is.EqualTo(player.CurrentHealth));
    }
}
```

### D. Performance tests (if framework present)

For systems with performance scenarios in the plan:
- Create `Assets/Tests/EditMode/<SystemName>PerfTests.cs`
- Use `Unity.PerformanceTesting` namespace, `[Performance]` attribute, `Measure.Method()`

### E. Mock / stub helpers

For every interface or abstraction identified in the mocking strategy section of the plan:
- Create `Assets/Tests/EditMode/Mocks/Mock<InterfaceName>.cs` with a minimal hand-rolled implementation
- Only generate mock files for interfaces that actually exist in the codebase

### F. CI automation script

Create `.github/workflows/unity-tests.yml` for GitHub Actions:

```yaml
name: Unity Tests

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main, develop]

jobs:
  test:
    name: Run Unity Tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          lfs: true

      - uses: game-ci/unity-test-runner@v4
        id: tests
        env:
          UNITY_LICENSE: ${{ secrets.UNITY_LICENSE }}
          UNITY_EMAIL: ${{ secrets.UNITY_EMAIL }}
          UNITY_PASSWORD: ${{ secrets.UNITY_PASSWORD }}
        with:
          projectPath: .
          testMode: all          # editmode + playmode
          artifactsPath: TestResults
          coverageOptions: generateAdditionalMetrics;generateHtmlReport;assemblyFilters:+<RuntimeAssembly>

      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: unity-test-results
          path: ${{ steps.tests.outputs.artifactsPath }}
```

Also create `scripts/run-tests-local.sh` — a Bash helper to run tests headlessly with the Unity Editor installed locally:

```bash
#!/usr/bin/env bash
set -euo pipefail
UNITY_PATH="${UNITY_PATH:-/Applications/Unity/Hub/Editor/2022.3.0f1/Unity.app/Contents/MacOS/Unity}"
PROJECT_PATH="$(pwd)"
RESULTS_DIR="$(pwd)/TestResults"
mkdir -p "$RESULTS_DIR"

run_tests() {
  local mode="$1"
  "$UNITY_PATH" \
    -batchmode -nographics -quit \
    -projectPath "$PROJECT_PATH" \
    -runTests \
    -testPlatform "$mode" \
    -testResults "$RESULTS_DIR/${mode}-results.xml" \
    -logFile "$RESULTS_DIR/${mode}.log"
}

run_tests editmode
run_tests playmode
echo "Results written to $RESULTS_DIR"
```

Create `Assets/Tests/TestRunnerSettings.json` if not present, enabling coverage and filtering options used in CI.
